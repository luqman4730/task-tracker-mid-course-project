# Comments Feature Plan

## 1. Data Model - where the comment models belong and how they fit existing patterns

Add comment schemas to `D:\Courses\AUB\AI-Assisted Coding\on-course project\task-tracker\app\models.py`, alongside `TaskCreate`, `TaskUpdate`, and `TaskResponse`.

Recommended models:

- `CommentCreate`
  - request model for creating a comment
  - fields: `author`, `body`
  - `model_config = ConfigDict(extra="forbid")`, matching the existing task request models
  - `author` should be stripped, required, non-blank, and 1-100 characters
  - `body` should be stripped or preserved with surrounding whitespace stripped, required, non-blank, and 1-2000 characters

- `CommentResponse`
  - response/storage model for comments
  - fields: `id`, `task_id`, `author`, `body`, `created_at`
  - `id` generated by the server as UUID4, matching task ID generation in `app\storage.py`
  - `created_at` generated by the server with `datetime.now(timezone.utc)`, matching task timestamp behavior in `app\storage.py`

Store comments in `D:\Courses\AUB\AI-Assisted Coding\on-course project\task-tracker\app\storage.py`. The current task store is process-local memory in `_tasks: dict[str, TaskResponse]`; comments should follow that style with a separate in-memory collection, likely `_comments: dict[str, CommentResponse]`.

Do not embed comments inside `TaskResponse` for the first version. Existing task routes currently return task objects only, and changing `TaskResponse` would alter every `GET /tasks`, `GET /tasks/{task_id}`, `POST /tasks`, and `PATCH /tasks/{task_id}` response.

## 2. API Routes - HTTP method, path, request body, response body, and error cases

Add routes in `D:\Courses\AUB\AI-Assisted Coding\on-course project\task-tracker\app\main.py`, where all current routes live.

| Method | Path | Request body | Response body | Status |
| --- | --- | --- | --- | --- |
| `GET` | `/tasks/{task_id}/comments` | none | list of `CommentResponse` | `200` |
| `POST` | `/tasks/{task_id}/comments` | `CommentCreate` | created `CommentResponse` | `201` |

`GET /tasks/{task_id}/comments`:

- Return comments for the task, probably oldest first by insertion order or `created_at`.
- Return `404` if `storage.get_task_by_id(task_id)` returns `None`, matching existing missing-task behavior.
- Return `200` with `[]` when the task exists but has no comments.

`POST /tasks/{task_id}/comments`:

- Validate the task exists before creating the comment.
- Accept only `author` and `body`.
- Generate `id`, copy `task_id` from the path, and stamp `created_at` in UTC server-side.
- Return `404` if the task does not exist.
- Return `422` for missing, blank, too-long, or unknown fields, matching existing Pydantic/FastAPI validation patterns.
- Reject client-supplied `id`, `task_id`, or `created_at` as unknown request fields through `extra="forbid"`.

Task deletion behavior should be defined before implementation. If `DELETE /tasks/{task_id}` remains as-is, comments could become orphaned unless `storage.delete_task()` also removes comments for that task.

**My Critique**
- Label: Right
- Notes: Fits the existing route and error-handling conventions in app/main.py. Comment ordering should be decided explicitly instead of left as "probably."

## 4. Frontend Changes - which files would change and what the user would see

Change `D:\Courses\AUB\AI-Assisted Coding\on-course project\task-tracker\frontend\index.html`. The frontend is currently a single HTML file with embedded CSS and JavaScript, a hard-coded `API_BASE = "http://localhost:8000"`, task cards, filters, drag-and-drop status changes, and a create/edit modal.

Recommended first UI:

- Add a "Comments" area to the existing edit modal.
- When a user opens a task for editing, fetch `/tasks/{task_id}/comments`.
- Show existing comments with author, body, and created time.
- Add author and body fields plus an "Add comment" action.
- After successful comment creation, refresh only the comments area or re-fetch the task's comments.
- For new unsaved tasks, hide or disable comments until the task has been created.
- Show API validation errors in the existing modal error area style.

Optional visible enhancement:

- Add a comment count or "View comments" control on each task card, but this would require either fetching comments per task or extending the API with counts. No comment-count endpoint is visible today.

## 5. Migration Notes - anything about existing task data or storage shape that must change

There is no confirmed database or durable persistence. `README.md`, `AGENTS.md`, and `app\storage.py` all indicate task data is stored in memory and lost when the process stops.

Required storage changes:

- Add a comments collection in `app\storage.py`.
- Update `storage._reset()` so tests clear comments as well as tasks.
- Decide whether `delete_task(task_id)` cascades comment deletion.
- Keep existing task response shape unchanged unless the team explicitly chooses to embed comments.

No data migration is needed for currently running data because the store is process-local memory. If persistence is added later, comments will need a real migration with a task reference, indexes by `task_id`, and cascade behavior.

**My Critique**
- Label: Right
- Notes: Correctly recognizes the current in-memory storage and storage._reset() requirement. Task-delete behavior must be decided before implementation to avoid orphaned comments.

## 6. Open Questions - at least three real decisions the team should make

1. Should comments be create/list only, or should the feature also support editing and deleting comments?

2. When a task is deleted, should its comments be deleted immediately, retained in a separate orphaned/audit state, or rejected by preventing task deletion while comments exist?

3. Should `GET /tasks` include comment counts, or should the frontend fetch comments only when a task is opened?

4. Should `author` be free text forever, or is this a temporary stand-in for future authentication/accounts?

5. Should comment ordering be guaranteed as oldest-first, newest-first, or unspecified insertion order?

6. Should comment `body` preserve leading/trailing whitespace exactly, or strip it like task titles currently do?

- Notes: The plan includes several real decisions, but it omits whether creating a comment should update the parent task's updated_at. Add that decision before implementation.

**Where the generic plan was still useful:** It was useful for early brainstorming and identifying possible API, validation, storage, and product decisions before inspecting the repository.
